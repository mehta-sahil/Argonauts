How this works — red team, blue team, and the simulation

This is a closed-loop attack/defense simulation of a distributed CVV enumeration attack on card-payment infrastructure. Everything runs on synthetic data in a sandboxed AWS account. No real cards, banks, merchants or payment networks are touched.

The vulnerability being modelled

When a card is authorized, only the issuing bank checks the CVV. It returns two independent signals to the merchant: an authorization decision (approved / declined, based on funds) and a separate CVV result code per ISO 8583 — M match, N no match, P not processed. Some merchants ignore the N. If the bank approves the funds and flags N, a lax merchant lets the charge through anyway. That is the gap the attacker exploits.

No single merchant sees enough failed guesses to notice (3–5 each, under any local rate limit). Only the issuer, counting mismatches per card across all merchants, sees the whole attack. Grounded in Ali et al., “Does the Online Card Payment Landscape Unwittingly Facilitate Fraud?” (IEEE S&P 2017).

Red team — the attacker

Has a list of stolen card numbers + expiry dates, but not the CVVs. Goal: recover a CVV without getting the card blocked.

Technique

  • Distribute guesses across merchant A / B / C so each merchant sees only a few failures.
  • Stay slow-and-low: keep mismatches per card under the issuer's velocity threshold (5).
  • Profile merchants from the two-part response — find which ones accept a charge despite a N code (merchant C here) and concentrate there.
  • Shape controllable features: small “does it authorize” amounts, varied timing, merchant rotation — per Lunghi et al., FRAUD-RLA (arXiv 2502.02290, 2025).

In this demo

The browser loops CVV 000→999 (common values first, or random) and sends POST {pan, expiry, cvv, merchant_id, amount} to the public issuer Lambda URL. The batch/agent version lives in sim/attacker_agent.py, with an optional Gemini 2.5 Flash mode that authors a fresh strategy per session (clamped to safe bounds).

Blue team — the issuer

Layer 1 — centralized velocity (deterministic)

  • Every CVV mismatch atomically increments cvvFailedAttempts on the card in DynamoDB, regardless of which merchant sent it.
  • DynamoDB Streams trigger a mitigation Lambda; at 5 mismatches the card is set BLOCKED and all further auths decline. This is the architecture Mastercard runs in production.

Layer 2 — behavioural ML (catches slow-and-low)

  • Every auth event is logged to a second table. A scoring Lambda recomputes, per card, rolling 1h / 24h / 7d features: mismatch rate, merchant fan-out and entropy, small-amount fraction, decline rate, “approved-but-N” fraction, inter-attempt timing, session bursts, a merchant historical N-rate, and an IsolationForest anomaly score.
  • A LightGBM model scores that vector to a risk_score (0–1), written back onto the card.
  • The mitigation Lambda blocks on cvvFailedAttempts ≥ 5 OR risk_score ≥ 0.86, tagging block_reason as threshold or model.
  • Feature families follow Whitrow 2009 and Bahnsen 2016; imbalance handling and time-ordered AUC-PR / Precision@k evaluation follow Dal Pozzolo 2018 and Davis & Goadrich 2006; the hybrid anomaly feature follows Carcillo 2021.

How the simulation is built

  • Cards: ~30 synthetic, Luhn-valid PANs with real test BIN prefixes, random CVVs and expiries, seeded into DynamoDB (MockIssuerDB). ~35% are “dead” (no funds) to match real stolen-dump characteristics. The attacker never sees the CVV column.
  • Issuer: a Python Lambda behind a public Function URL. Checks PAN + expiry + CVV, returns the ISO 8583-style two-part response, increments the mismatch counter. A local mirror (sim/mock_gateway.py) runs the identical logic offline for training-data generation.
  • Merchant posture (strict / moderate / lax) is applied client-side, in this page — the issuer is posture-agnostic, just like real life.
  • Model training: a benign-traffic generator and an attack-campaign generator run against the local mirror to produce a labelled event log; the model is trained and evaluated offline (ml/), then the exact same feature code is packaged into the scoring Lambda so offline and online scores cannot diverge.
  • Safety: one sandboxed AWS account, Lambda concurrency capped, a $1 budget alarm, synthetic data only.
